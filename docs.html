START

Uno docs

Uno is a coding agent for the terminal. You tell it what you want in plain words; it reads your project, edits files and runs commands until the job is done. These docs explain every part of it in plain language, with a picture, an example and real use cases for each.

Where to start

5 MINUTESQuickstartInstall, add a key, finish your first real task. THE CORE IDEAHow Uno worksStep through one task, call by call. 14 RECIPESUse casesFix a test, learn a codebase, run in CI, and more. READ THISThe safety modelWhat Uno can and cannot do to your machine. DECIDEWhich one do I use?Instructions, memory, skills, hooks or MCP. WHYDesign decisionsThe choices behind Uno, and what they cost.

What Uno is good at

  • Everyday coding. Fix a bug, add a test, rename across files, explain a module you have never seen.
  • Staying cheap. Uno sends about 3,500 tokens of standing instructions with each request, where Claude Code sends about 46,000. On ten practice exercises with the same model, Uno spent $0.35 to Claude Code's $1.11 and solved the same ten.
  • Staying out of trouble. It asks before changing things, runs shell commands in a sandbox, can undo every file change and stops at a spending cap.
  • Scripts and CI. uno -p "…" runs one task with no questions and prints the answer, or JSON.

What Uno is not

  • Not smarter than its model. The model does the thinking. Uno is the harness around it: the tools, the guards and the memory.
  • Not finished. Windows, a to-do list, asking you questions mid-task, scheduled runs and streamed JSON are still to come. See What we didn't build.
  • Not an IDE plugin or a cloud service. It is one 3 MB program that runs in your terminal, with your own API key.

Three ways in. All three install the same 3 MB program.

Pick one

# the installer: puts uno in ~/.local/bin and can update itself
curl -fsSL https://unocode.motiontic.com/install.sh | sh

# Homebrew
brew install motiontic/tap/uno

# npm (Node 18 or later)
npm i -g @motiontic/uno
ChooseWhenUpdates with

HomebrewYou manage tools with brew alreadybrew upgrade uno

Machines

  • macOS and Linux, on arm64 and x86_64. The Linux build runs on any distribution.
  • Linux needs bubblewrap for the sandbox: sudo apt install bubblewrap or sudo dnf install bubblewrap. Without it, every command asks before it runs.
  • Windows is not supported yet.

Installer options

  • UNO_VERSION=0.1.1 installs a particular version.
  • UNO_INSTALL_DIR=/somewhere installs outside ~/.local/bin. If the folder is not on your PATH, the installer prints the line to add.
  • It checks the download against the release's checksums, and against its signature when minisign is installed.

Verify

uno --version      # prints the version
uno settings       # shows the settings in effect and where each came from

DESIGN DECISION · D36

The source is private, but releases are public and signed. Quickstart

From nothing to a fixed bug in five minutes.

IN ONE LINEAdd a key, open uno in a project, describe the job, answer y / a / n when it asks.

1. Give it a key

Uno talks to the model with your own API key. Put it in your config folder so it works in every project:

mkdir -p ~/.config/uno
echo 'ANTHROPIC_API_KEY=sk-ant-...' >> ~/.config/uno/.env
chmod 600 ~/.config/uno/.env

Other providers: OPENAI_API_KEY, GOOGLE_API_KEY, or OPENAI_COMPAT_API_KEY for any OpenAI-compatible server. See Providers and models.

2. Open a chat in your project

cd ~/code/my-app
uno

You see the Dot screen: Uno in large dots, then cards for this folder, the guards and the budget. Type what you want and press Enter.

3. Ask for something real

 UNO · MY-APP
the signup form accepts emails with spaces in them. fix it and add a test
grep "validate_email" src/
src/forms/signup.ts:18 export function validateEmail(v: string) {
read src/forms/signup.ts
edit src/forms/signup.ts (+2 −1)
Allow this edit? y once · a all edits this session · n no
a
write src/forms/signup.test.ts

✓ 6 tests passed
Trimmed the value and rejected inner whitespace in validateEmail. Added signup.test.ts with three cases; all six tests pass.

4. Look, keep or undo

  • git diff shows what changed. Uno never commits for you unless you ask.
  • /undo in the chat (or uno undo later) puts back the newest file change; /undo all puts back the whole session's.
  • /cost shows what the task cost.

No chat, no questions: it prints the answer and exits. Anything that would need your say-so is refused, so this is safe to try. See Headless runs.

START

How Uno works

Uno is a loop. It sends the conversation to the model; the model either answers or asks for a tool; Uno checks the tool call, runs it, and sends the result back. That is all.

IN ONE LINEModel decides, guard checks, tool runs, result goes back. Repeat until the model answers without asking for a tool.

Step through a real task

The parts

PartIts jobRead more
The loopSends the conversation, streams the reply, runs the tools the model asks for, repeatsthis page
The modelDecides every next step. Uno never scripts a plan for itProviders
The toolsRead, write, edit, search, shell, web, helpers, memory searchTools
The guardTrust, rules, mode and sandbox, checked on every callSafety model
The storeSaves every message as it happens, so a session can be resumedSessions
The screenShows you all of this, and asks your permissionDot screen

Rules the loop follows

  • Read-only tools run together; changing tools run one at a time. Three searches finish in the time of one, and two edits never race.
  • The tool list never changes during a session. That keeps the start of every request identical, so the provider can cache it. See Context and cost.
  • A reply cut off by the length limit never runs its tool calls. Half a command is worse than none.
  • Network errors are retried with backoff, up to five attempts in all, but only before any of the reply has been shown.
  • Turns are capped. --max-turns stops a run that goes round too long.
  • You can type while it works. Your message is added at the next tool result, without stopping the turn. Esc stops it.
DESIGN DECISION · L1, D2

No workflow graph, no "plan, act, critique" scaffolding, no agent framework. Current models plan on their own, and hard-coded steps get in their way. Uno's job is to give the model good tools and safe limits, then step aside. The whole loop is under a thousand lines of Rust that talk to each provider over plain HTTPS.

CORE CONCEPTS

Tools

Tools are the model's hands. The model cannot touch your machine directly; it can only ask Uno to run one of a short, fixed list of tools.

IN ONE LINESix core tools (read, write, edit, grep, glob, bash) plus web, helpers, memory search and MCP. Every call goes through the guard.

The list

ToolWhat it doesAsks?
readReads a file, up to 2,000 lines or 50 KB at a time. Reads images toono, inside the project
grepSearches file contents, skipping what .gitignore skipsno
globFinds files by name pattern, newest firstno
writeCreates or replaces a file. A snapshot is taken firstby mode
editReplaces exact pieces of a file, all or nothing. OpenAI models get apply_patch insteadby mode
bashRuns a shell command, in the sandbox. Long output is cut to its end and saved to a fileonly to leave the sandbox
web_fetchReads one public web page as textyes, unless a rule covers the site
taskHands a side job to a helper agentno; the helper's own calls are checked
recallSearches past sessionsno
mcp_search, mcp_callFind and call tools on your MCP serversmcp_search no; mcp_call yes, unless a rule allows it

Web search is not in the list: it is the provider's own search, run on their side. The browser is not either: Uno drives it through bash, taught by a bundled skill. See Web and browser.

Use cases

Find before you fix

Ask "where do we parse dates?" The model runs several greps at once and reads only the hits.

uno -p "where do we parse dates?"

Rename across a codebase

One edit per file, each all or nothing, each undoable.

uno -p "rename getUser to fetchUser everywhere"
DESIGN DECISION · L3

Keep the core tiny. Strong coding agents get by with a handful of tools, and every extra tool costs tokens on every request and gives the model one more thing to get wrong. A new tool has to justify itself. That is why the browser is a skill, not a tool, and why all MCP servers share two tools.

CORE CONCEPTS

Context and cost

Every request sends the model the whole conversation again. What you pay depends mostly on how much is sent, and how much of it the provider can reuse from its cache.

IN ONE LINEUno keeps the start of every request byte-for-byte the same, so the provider charges about a tenth for it after the first time.

What one request holds

Where the money goes

  • The standing part. System prompt and tool descriptions: about 1,800 tokens, or about 3,500 with the provider's web search on. Claude Code sends about 46,000.
  • Your project's part. AGENTS.md, the first 100 lines of memory, and the list of skills. Sent once, at the start, then cached.
  • The conversation. Grows each turn. Tool output is the biggest part: a test log can be thousands of tokens.

How Uno keeps the cache warm

  1. Nothing early ever changes. The tool list is fixed for the session. Skills, plan mode and reminders arrive as new messages at the end, never as edits to the start.
  2. Project instructions go in the first user message, not the system prompt, so the system prompt is identical in every project and every session.
  3. On Anthropic Uno marks cache points on the tools, the system prompt and the newest message. On OpenAI it sends a stable cache key per session. Gemini caches on its own.
  4. Shortening reuses the cache too: the summary is asked for on the same cached prefix, with the same model.
 -P RUN · STATUS LINE
[done: 6 turns, 3912 in, 1104 out, 41280 cached, $0.0187, session a1f3…]

Every -p run with text output ends with this line on stderr. The cached figure is the part you paid about a tenth for. Illustrative numbers.

Use cases

Cheap long sessions

Stay in one chat for a related run of tasks: each turn reuses the cache from the last.

uno --resume

Leaner still

Turn off provider search when you don't need it. It saves about 1,700 tokens a request on Anthropic.

uno --no-search
DESIGN DECISION · M5, M7, M15

Append-only is a hard rule. Any change to the tools or system prompt mid-session throws the whole cache away, and the next request costs full price. So plan mode is a permission setting rather than a different tool list, MCP servers hide behind two fixed tools, and skills are read as files instead of being added to the prompt.

CORE CONCEPTS

Compaction

Every model has a limit on how much it can read at once: its context window. When a long conversation gets close, Uno shortens it so the work can carry on.

IN ONE LINEFirst drop old tool output, then, if that is not enough, replace the conversation after your first message with a summary.

What happens, in order

  1. Prune. Old tool output (file contents, test logs) is the bulk of most long conversations, and the model has already acted on it. Uno replaces old results with a short note. The newest ones stay.
  2. Summarise. If that is not enough, Uno asks the same model, on the same cached prefix, for a summary in fixed sections: the goal, decisions made, files touched, work still open, and the exact next step. The summary replaces everything after your first message, and the current text of up to five recently touched files is attached so the work can carry on.
  3. Carry on. Tool calls and their results always stay in pairs, and a resumed session loads the short history.
  4. Last resort. If even a summary will not fit, the run stops with too_long, the work so far saved, and tells you to start a new run with what is left.

Type /compact to shorten now, for example before starting the next part of a big task. --window <tokens> sets the window for a model Uno does not know, or makes shortening happen earlier.

Use cases

A long migration

Hours of edits and test runs in one chat. The old logs get pruned, the plan and decisions survive in the summary.

uno

Before the next chapter

Finished one feature, starting another in the same chat? Compact first so the new work starts lean.

/compact
DESIGN DECISION · M8, M9, M10

Summarise with the same model on the same prefix, not a cheaper model: the cached prefix makes it cheap anyway, and a cheaper model forgets more. Prune before summarising, because dropping old output loses almost nothing and costs nothing. Use fixed sections, because free-form summaries quietly drop the things you need later.

CORE CONCEPTS

Sessions and undo

Every conversation is saved as it happens, one line per message. Every file change is snapshotted before it is made. So you can come back to any conversation, branch it, or put your files back.

IN ONE LINE--resume continues, --fork branches, undo puts files back.

Commands

uno sessions                         # this folder's sessions: id, age, messages, first prompt
uno --resume                         # continue the newest
uno --resume a1f3 -p "now add docs"  # continue a given one, as a one-shot run
uno --fork a1f3 -p "try it with a cache instead"   # branch, original unchanged
uno undo                             # put back the newest file change
uno undo --all                       # put back every change of the newest session
uno undo --force                     # even if something else changed the file since

In the chat: /sessions, /resume, /fork, /undo, /undo all.

What undo covers, and what it does not

  • Covered: every change made with write, edit or apply_patch, including changes to long-term memory.
  • Not covered: files changed by shell commands (sed -i, mv, a code generator). Uno tells the model to change files with its file tools for this reason. If a command changed a file since, undo stops and names --force.
  • Safe with your own edits: if you changed the file after Uno did, undo refuses rather than overwrite your work.

Use cases

Pick up tomorrow

Close the terminal. Tomorrow, the whole conversation is still there.

uno --resume

Try two approaches

Fork once for each idea, compare the diffs, keep the better one.

uno --fork a1f3 -p "use a trie instead"

Bad idea, roll back

The refactor went sideways. Undo the whole session's file changes in one go.

uno undo --all

A crash mid-task

A session cut off mid-tool-call resumes cleanly: the unfinished calls are marked interrupted.

uno --resume
DESIGN DECISION · D4, M16, M17

Sessions are plain append-only JSONL, one message per line with an id and parent id. Resume is "read the lines", fork is "copy the file", and a crash loses at most one half-written line. Undo uses a snapshot before each file-tool change rather than a shadow git repo: cheap, always on, and honest about what it cannot cover.

CORE CONCEPTS

The Dot screen

The chat fills the terminal and is drawn in dots with one accent colour. Cards across the top show what Uno is doing, how full the context is and what has been spent.

IN ONE LINECards on top, conversation below, permission questions at the bottom. Prefer your terminal's own scrollback? Use --screen chat.

The parts

  • The welcome. A new chat opens on Uno in large dots, then cards on this folder (branch, the instruction files and skills Uno read), the guards (mode, sandbox, trust, undo) and the budget.
  • The strip. From the first prompt, four cards run across the top: UNO, 02 AGENT, 03 CONTEXT, 04 BUDGET. Under 24 rows they fold to one line.
  • The question. A permission question opens at the bottom of the conversation.
  • Leaving. The conversation is printed into the terminal, so your scrollback keeps it.

The scrolling chat

The full screen takes over your terminal's scrollback, selection and search while it is open. If you would rather keep those, the scrolling chat has the same look in plain output, and /status, /context and /budget print the cards on demand.

uno --screen chat                      # once
export UNO_SCREEN=chat                 # this shell
{ "ui": { "screen": "chat", "accent": "yellow" } }   # always, in ~/.config/uno/settings.json

accent is red or yellow. Windows smaller than 80 × 14 always get the scrolling chat. NO_COLOR keeps the dots and drops colour.

DESIGN DECISION · D29 → D35, D37

Uno started as a plain scrolling chat, so copy and search worked like any terminal program. Mockups showed that a full screen with live cards made the agent's state readable at a glance, so it became the default, with the scrolling chat one setting away. Cards moved from the side to a strip on top when most real windows turned out too narrow for a sidebar.

CORE CONCEPTS

Providers and models

Uno speaks four model APIs directly. You pick a model by name; Uno works out which provider serves it.

IN ONE LINE--model picks the model; add --provider openai-compat --base-url … for anything else that speaks OpenAI's chat format.
ProviderKeyCachingWeb search
AnthropicANTHROPIC_API_KEYexplicit cache pointsyes
OpenAIOPENAI_API_KEYautomatic, stable key per sessionyes
GeminiGOOGLE_API_KEY or GEMINI_API_KEYautomaticGemini 3 models
OpenAI-compatibleOPENAI_COMPAT_API_KEYnone assumedno

The default model is claude-sonnet-5. Gemini support is built but not yet tested against the live service.

Examples

uno --model claude-haiku-4-5                        # cheap and quick
uno --model gpt-6-luna                              # OpenAI
uno --provider openai-compat --base-url http://localhost:11434/v1 --model qwen3   # a local server
/model claude-sonnet-5                              # in the chat, from the next turn

Keys are read from the environment, then a .env in the folder you run uno in, then ~/.config/uno/.env. Your keys are never passed to hooks, MCP servers or helper processes.

Use cases

Cheap model for chores

Renames, docs, small tests: a small model does them for a fraction of the price.

uno --model claude-haiku-4-5 -p "add docstrings to src/util"

Keep code on your machine

Point Uno at a model server on your own machine or network.

uno --provider openai-compat --base-url http://gpu-box:8000/v1 --model qwen3
DESIGN DECISION · D2, D3, D7

No vendor SDKs. Each provider has a thin adapter that turns Uno's one internal message format into that provider's JSON and back, over plain HTTPS. The agent loop never sees provider-specific shapes, so adding a provider never touches the loop, and the binary stays about 3 MB.

SAFETY

The safety model

A coding agent runs commands a model chose, on your machine. Uno puts five layers between the model and your machine, and is plain about what each one does not stop.

IN ONE LINETrust gate, rules, mode, sandbox, then undo and the spending cap behind them. Deny always wins.

The layers

LayerStopsPage
Trust gateA cloned repo's own settings, hooks and MCP servers from taking effect until you say soTrust
RulesCalls you have forbidden (deny), or want asked about (ask)Permissions
ModeEdits and risky commands without your say-soPermissions
SandboxShell commands writing outside the project, reading secrets, reaching the networkSandbox
UndoA bad file change from being permanentSessions and undo
Spending capA runaway loop from running up a billSpending cap

Always true, in every mode

  • .env files and key files are never read by Uno's file tools.
  • Changes under .git/, .uno/ and .claude/ ask, because they steer the tools themselves. With -p they are refused, plan mode refuses them, and only bypass mode lets them through.
  • The model cannot run uno trust for itself, even in bypass mode.
  • A deny rule holds even in bypass mode.
  • Your API keys never reach hooks, MCP servers or the model.
  • Web pages, MCP results and recalled sessions are marked to the model as data, not instructions.

What it does not stop

READ THIS ONCE

A command you allow runs unconfined. --allow "bash(npm install)" lets that command run outside the sandbox, on your machine, with your network. Keep rules narrow.

The model can be talked into things. A malicious README or web page can try to steer it. The gates limit what it can do, not what it wants to do; read what you approve.

Shell changes are not undoable. Only changes made with Uno's file tools are snapshotted.

MCP servers and hooks run outside the sandbox. They are programs you chose to run; trust them as you would any program.

Linux and Windows are less tested. The macOS sandbox has run for real; Linux needs bubblewrap; Windows has no sandbox yet.

DESIGN DECISION · F, D14, D26

Several thin layers, each easy to reason about, rather than one clever classifier. The order is fixed (trust, then rules, then mode, then sandbox), so you can always predict the outcome. The network is off in the sandbox by default because exfiltration is the worst thing a tricked model can do.

SAFETY

Permissions and modes

The mode sets how much Uno does without asking. Rules carve exceptions: things that always run, always ask (except in bypass mode), or never run.

IN ONE LINEdeny beats ask beats allow; whatever no rule covers, the mode decides.

Try the modes

Answering a question

KeyMeans
yYes, this once
aYes for the rest of the session: on an edit, every file change in the project; on a command, every command that starts the same way; on a web fetch, that site
nNo. The model is told, and finds another way or asks you

For MCP calls there are more: a this tool, s every tool on this server, m every MCP tool, for the session.

Try the rules

Writing rules

  • tool covers every call of a tool: web_fetch, bash, edit.
  • bash(cargo test) covers commands that start with those words. Pipes and && are split, and each command must be covered.
  • web_fetch(*.github.com) covers the subdomains of github.com; add web_fetch(github.com) for the site itself.
  • mcp__github__create_issue, mcp__github or mcp cover one MCP tool, a server, or all of them.
  • Claude Code's WebFetch(domain:docs.rs) spelling works too.

Rules live in permissions in ~/.config/uno/settings.json, or in a trusted project's .uno/settings.json. For one run, use --allow:

uno -p "fix the lint errors" --allow "bash(npm run lint)"

Use cases

Look but don't touch

Exploring a codebase you don't own, or planning a big change first.

uno --mode plan

Trust the edits, watch the commands

You will review with git diff anyway.

uno --mode accept-edits

Never push

One rule, in every mode, even bypass.

"deny": ["bash(git push)"]

A throwaway container

Nothing to protect inside it. Deny rules still hold.

uno --dangerously-skip-permissions
DESIGN DECISION · D31, R9

a covers the whole group (all edits, or one command prefix) because answering once per file was tiring enough that people stopped reading the questions. Plan mode is a permission mode, denied at the moment of the call, rather than a different set of tools, so switching to it does not throw away the prompt cache.

SAFETY

The sandbox

Shell commands run inside the operating system's own sandbox: Seatbelt on macOS, bubblewrap on Linux. Inside it, a command can work on your project and nothing else.

IN ONE LINEWrite the project and temp. Read no secrets. No network. Because of that, sandboxed commands run without asking.

Inside the sandbox, a command

  • can read your files and write inside the project and temporary folders;
  • cannot write anywhere else: not your home folder (except package and build caches such as ~/.cargo/registry, ~/.npm and ~/.cache), not Uno's own settings, and not .git/hooks, .uno or .claude inside the project;
  • cannot read .env files or credential folders such as ~/.ssh and ~/.aws;
  • cannot reach the network.

When a command needs more

Installing packages needs the network. The model can ask to run a command outside the sandbox, and that always asks you:

 UNO
bash npm install zod (outside the sandbox)
`npm install zod` would run outside the sandbox. Allow? y · a · n
  • --allow "bash(npm install)" or a rule lets that command run unconfined without asking. Keep it narrow.
  • --no-sandbox turns the sandbox off for a run; every command then asks.
  • "sandbox": {"enabled": false} in settings does the same, always.

Use cases

Let it run the tests freely

Tests, builds, linters: all local, so all sandboxed, so no questions.

uno -p "make the failing tests pass"

Install one thing

Allow just that command, just this run.

uno --allow "bash(cargo add)"
DESIGN DECISION · D14

Network off by default, ask to allow. Most of what a coding agent runs (tests, builds, greps) needs no network, and the worst outcome of a tricked model is sending your code or keys somewhere. The operating system enforces it, not the prompt, so no clever wording gets around it.

SAFETY

Trust

A project can carry its own Uno settings, hooks and MCP servers. Those are code that runs on your machine, so they take effect only in folders you have trusted.

IN ONE LINEClone a repo, read its .uno/ folder, run uno trust. Change those files, and you trust again.
uno trust             # trust this folder's settings, hooks and MCP servers as they are now
uno trust --status    # trusted? changed since?
uno trust --remove    # stop trusting it
  • Trust is recorded against a fingerprint of those files. If any of them change, the folder is untrusted until you look and trust again.
  • An untrusted folder says what it declares, for example how many MCP servers, so you know what you are missing.
  • Instruction files and skills load without trust: they are text, and whatever they lead the model to do still goes through the guard.
  • The model cannot run uno trust for itself, in any mode.

Use cases

Your team shares a setup

Commit .uno/settings.json with the test command allowed and a lint hook. Each teammate trusts once.

uno trust

A stranger's repo

Don't trust it. Uno still reads its AGENTS.md and works normally, with your own settings.

uno --mode plan
DESIGN DECISION · F

Cloning a repo should never be enough to run its code. A project's hooks and MCP servers are programs written by whoever wrote the repo. The fingerprint means a later git pull that adds a hook does not slip in under an old "yes".

SAFETY

The spending cap

Every model call is checked against a cap before it is sent and recorded after it returns. When the next call would go over, Uno stops.

IN ONE LINE$5.00 in total until you raise it with UNO_SPEND_CAP_USD; --max-cost for a single run.
uno spend                        # spent so far, against the cap
export UNO_SPEND_CAP_USD=50      # raise the total cap
uno -p "..." --max-cost 0.50     # stop this run before it spends more than 50 cents
/cost                            # in the chat: this chat and the total
  • Helper agents spend from the same meter, and each gets at most a quarter of what is left.
  • Web searches are counted too, at about a cent each (1.4 to 3.5 cents on Gemini).
  • A model missing from Uno's price table is charged at a deliberately high rate, so the total can overstate what you really spent. Your provider's dashboard has the true figure.

Use cases

A nightly job with a ceiling

Whatever happens overnight, it cannot cost more than this.

uno -p "update deps and fix breakages" --max-cost 1

Trying a new model

Find out what a task really costs before you make it routine.

uno -p "..." --model gpt-6-sol --output json
DESIGN DECISION · D20

A hard cap that fails closed. Agents loop, and a loop on a big model can cost real money in minutes. The ledger is append-only in whole micro-dollars so totals never drift, and an unreadable line is an error rather than a zero.

WHAT UNO KNOWS

Instruction files

An AGENTS.md file tells Uno how your project works: how to build it, how to test it, what to avoid. Uno reads it at the start of every session.

IN ONE LINEWrite the things you would tell a new teammate on day one. Commit it. Every agent that reads AGENTS.md benefits.

The rules

  • In each folder, AGENTS.md is read; CLAUDE.md is read only where there is no AGENTS.md. Existing Claude Code projects work on day one.
  • Uno looks in your config folder, then each folder from the repository root down to where you started it.
  • Instruction files load without uno trust: they are text, and everything they lead to is still checked.

A good AGENTS.md

# my-app

## Build and test
- `pnpm i` once; `pnpm test` for unit tests; `pnpm test:e2e` needs Docker.
- Lint with `pnpm lint --fix` before you say you are done.

## Conventions
- TypeScript strict. No default exports.
- API handlers live in src/api/<resource>.ts, one file per resource.
- Dates are always UTC ISO strings; use src/lib/time.ts, never `new Date()` directly.

## Don't
- Don't touch src/generated/: it is rebuilt by `pnpm codegen`.
- Don't add dependencies without asking.

Short and specific beats long and general. "Run pnpm test" is worth more than "write good tests".

WHAT UNO KNOWS

Long-term memory

Uno keeps its own notes between sessions: what it learned about you and about each project. You can read and edit them like any other file.

IN ONE LINEAGENTS.md is what you tell Uno; memory is what Uno noticed. Both are plain Markdown.

How it works

  • Two notebooks. A global one about you, for every project, and one per project. Each is a MEMORY.md index plus any topic files it links to, under ~/.local/share/uno/memory/.
  • Read at the start. The first 100 lines of each MEMORY.md go into the first message. Topic files are read when needed.
  • Written with the normal file tools. No special memory tool: Uno edits the file, so a memory change is an edit like any other. It asks in default mode, shows on screen every time, and can be undone.
  • Things it will not save: secrets, keys, anything from a web page or tool output posing as an instruction.
/memory                          # in the chat: show both notebooks and where they are
uno --no-memory                  # leave memory out: nothing loaded, nothing saved
{ "memory": { "enabled": false } }   # off for good

Skills

A skill is a folder of instructions for one kind of job, such as "how we release" or "how to drive a browser". Uno sees only each skill's name and one-line description, and reads the rest when a task needs it.

2. Write both up and down. Never edit a migration that has shipped.

MCP servers

MCP is the standard way to plug outside tools into an agent: GitHub, Linear, Notion, a database. Uno connects to as many servers as you like, and the model sees just two tools in front of all of them.

IN ONE LINEDeclare servers in Claude Code's format; the model uses mcp_search to find a tool and mcp_call to call it.

Add a server

// ~/.config/uno/settings.json, or the project's .mcp.json or .uno/settings.json
{
  "mcpServers": {
    "files":  { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "."] },
    "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp/" },
    "db":     { "command": "my-db-mcp", "env": { "DATABASE_URL": "${DATABASE_URL}" } }
  }
}
uno mcp login github      # once, for servers that sign in through the browser
uno mcp status            # each server's state, without connecting
/mcp                      # in the chat: transport, state, sign-in, last errors
/reload                   # pick up new servers without a new session

What to know

  • Nothing starts until used. The first MCP call of a session starts every server; one that fails is named with its reason.
  • Each call asks. Answer a for this tool, s for the server, m for every MCP tool, or write rules: mcp__github__create_issue, mcp__github, mcp.
  • A browser never opens by itself. A server that needs sign-in mid-run is reported: needs sign-in: run uno mcp login <name>.
  • Secrets stay out of sight. Tokens live in ~/.config/uno/mcp-tokens.json, readable by you only, and never reach the model or the session file.
  • Trust. A project's servers load only after uno trust. Servers run outside the sandbox.

Hooks

Hooks are your own commands, run by Uno at fixed points in a turn. They are how you make something happen every time, rather than when the model remembers.

IN ONE LINEClaude Code's hook contract: JSON on stdin, exit code 2 blocks. Five events. Hooks can only make things stricter.
{
  "hooks": {
    "PreToolUse":  [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "~/bin/no-rm.sh", "timeout": 10 }] }],
    "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "npx prettier --write \"$(jq -r .tool_input.path)\"" }] }]
  }
}
#!/bin/sh
# ~/bin/no-rm.sh: refuse any shell command that contains rm -rf
if jq -r .tool_input.command | grep -q 'rm -rf'; then
  echo "rm -rf is not allowed here; delete files one by one" >&2
  exit 2
fi
EventWhenExit 2, or "decision": "block"
PreToolUsebefore a tool runsthe call is not run; the reason reaches the model
PostToolUseafter it ranthe result is marked as an error, with the reason
UserPromptSubmitwhen you send a promptthe prompt is not sent; you see why
Stopwhen the model is about to finishit carries on with the reason, at most three times
SessionStartonce per runnothing to block; output is added as context
  • Hooks live in ~/.config/uno/settings.json, .uno/settings.json or .claude/settings.json; project ones only after uno trust.
  • Matchers use Claude Code's tool names: Bash is bash, Edit covers edit and apply_patch. Uno's edit input is path and edits, not file_path.
  • A PreToolUse hook that times out or cannot start blocks the call. Default timeout 30 s.
  • Hooks run outside the sandbox, in the project folder, without your API keys.

Headless runs

uno -p runs one task with nobody watching: no screen, no questions. It prints the answer and exits with a code your script can check.

IN ONE LINEEdits go ahead (and can be undone); anything else that would ask is refused; exit code 2 tells you something was refused.

Basics

uno -p "add a test for parse_date"                  # one task
uno -p "review this diff for bugs: $(git diff)"     # the diff goes in the prompt
uno -p "fix the lint errors" --allow "bash(npm run lint)"
uno -p "summarise src/billing" --mode plan           # read-only
uno -p "..." --output json | jq .result              # for scripts

uno -p "plan the migration, write it to PLAN.md"

DESIGN DECISION · D26

A headless run starts in accept-edits. Asking before every edit with nobody there would make -p useless, and edits stay inside the project and can be undone. Everything else that would ask is refused rather than allowed, and the exit code says so, so a script never silently does less than you think.

AUTOMATE

CI and scripts

Because uno -p never waits for input and always ends with a clear exit code, it drops into CI jobs, git hooks and cron.

IN ONE LINEInstall with the one-liner, pass the key as a secret, cap the cost, check the exit code.

A CI job that fixes lint

# .github/workflows/uno-lint.yml
name: uno lint fix
on: workflow_dispatch
jobs:
  fix:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: sudo apt-get install -y bubblewrap
      - run: curl -fsSL https://unocode.motiontic.com/install.sh | sh
      - run: |
          ~/.local/bin/uno -p "run the linter and fix every error it reports" \
            --allow "bash(npm run lint)" --max-cost 0.50 --output json > uno.json
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          UNO_SPEND_CAP_USD: "2"
      - run: jq -r .result uno.json >> "$GITHUB_STEP_SUMMARY"
      - run: git diff --stat

Add a step that commits or opens a pull request if you want the fix kept. Uno does not push on its own.

MIND THE ALLOW RULE

bash(npm run lint) runs whatever package.json says lint is, outside the sandbox, and Uno can edit package.json. Prefer naming the tool itself, such as bash(npx eslint), in a job that holds secrets.

A pre-commit review

#!/bin/sh
# .git/hooks/pre-commit: ask Uno to look over the staged diff, read-only
uno -p "list real bugs in this diff, or say LGTM: $(git diff --cached)" --mode plan --model claude-haiku-4-5

A very large diff can be too long for one argument (128 KB on Linux). Pipe it instead, without -p: the piped text is the whole prompt.

{ echo "list real bugs in this diff, or say LGTM:"; git diff --cached; } | uno --mode plan

A nightly job with cron

# crontab -e
0 3 * * * cd ~/code/my-app && uno -p "update minor dependencies and make the tests pass" --max-cost 1 >> ~/uno-nightly.log 2>&1

Check the result in a script

uno -p "make the tests pass" --output json > out.json
case $? in
  0) echo "done: $(jq -r .cost_usd out.json) USD" ;;
  2) echo "finished, but $(jq .refused out.json) calls were refused" ;;
  3) echo "stopped early: $(jq -r .exit out.json)" ;;
  *) echo "failed" ;;
esac

GUIDES

Best practices

Habits that make Uno faster, cheaper and more right.

Prompting

  • Say what done looks like. "Fix it and run the tests" beats "fix it".
  • Say what must not change. "Don't touch the public API." "Fix the code, not the test."
  • Point at the place when you know it: "in src/api/orders.ts".
  • Plan big things first. --mode plan, agree, then switch to accept-edits.
  • Steer, don't restart. Type while it works; your words arrive at the next tool result.

Cost

  • Use a small model for chores, a big one for design and debugging.
  • Stay in one session for related tasks: the cache does the rest.
  • Use helpers for big reads; only the report enters your conversation.
  • /compact between unrelated parts of a long session.
  • --no-search when the web is not needed.

Safety

  • Keep the sandbox on; most commands never need to leave it.
  • Prefer narrow rules (bash(npm run lint)) over wide ones (bash).
  • Add deny rules for the things that would really hurt: git push, deploy scripts.
  • Don't trust a repo you have not read.
  • Commit before a big task, so git is your second undo.

Project setup

  • A short AGENTS.md with the build, test and lint commands.
  • Skills for procedures you repeat; hooks for things that must always happen.
  • Committed .uno/settings.json so the team shares one setup.

DESIGN

Design decisions

Every big choice behind Uno, why it was made, and what it costs. The IDs match the project's decision log, so you can trace each one back.

THE THEMESmall core, honest limits, and never pay twice for the same tokens.
D1

Rust, one static binary

CHOICE
Write Uno in Rust and ship one file per machine.
WHY
No runtime to install, no garbage collector, direct access to the OS sandboxes. Starts in under 4 ms; about 3 MB on disk and in memory while idle.
COST
Slower to write than TypeScript, and fewer people can contribute.
D2

No frameworks, no vendor SDKs

CHOICE
Talk to each provider over plain HTTPS and server-sent events.
WHY
The core loop is under a thousand lines; frameworks add weight and decide things the model should decide.
COST
Each provider's new features must be added by hand.
D3

One message format inside

CHOICE
One internal format of content blocks; a thin adapter per provider.
WHY
The loop never sees provider JSON, so a fifth provider never touches it.
COST
Provider-only features need a place in the shared format first.
M7

The prompt is append-only

CHOICE
Never change the system prompt or tool list mid-session. Everything new arrives as a message at the end.
WHY
Any change at the start throws the provider's cache away, and cached tokens cost about a tenth.
COST
Some features take odd shapes: plan mode is a permission, MCP hides behind two tools, skills are file reads.
M15

Instructions in the first user message

CHOICE
Put AGENTS.md, memory and the skills list in the first user message, not the system prompt.
WHY
The system prompt is then identical in every project, so it caches everywhere.
COST
Some models weigh system-prompt text slightly more.
L3

Two tools for all of MCP

CHOICE
mcp_search and mcp_call front every server.
WHY
About 250 tokens however many servers you add, and adding one never breaks the cache.
COST
One extra step the first time the model uses a tool.
R9

Plan mode is a permission mode

CHOICE
In plan mode, file changes (except the plan) and shell commands are refused at the moment of the call; the tools stay the same, and MCP calls and web fetches still ask as usual.
WHY
Switching modes keeps the cache. Studies found plan mode is more about safety and agreement than better results, so it stays minimal.
COST
The model may try a change and be told no, which costs a turn.
D14

Sandbox network off by default

CHOICE
Shell commands run with no network unless you allow one to leave the sandbox.
WHY
Exfiltration is the worst outcome of a tricked model, and most coding commands need no network.
COST
Installs ask, or need a rule.
D26

Headless runs start in accept-edits

CHOICE
With -p, project edits go ahead; anything else that would ask is refused, and the exit code says so.
WHY
Asking with nobody there makes -p useless; edits are inside the project and undoable.
COST
A careless prompt can still rewrite a lot of files. Commit first.
D31

One "a" covers the group

CHOICE
a allows all edits, or one command prefix, for the session.
WHY
Asking per file trained people to press yes without reading.
COST
A broader yes than one file.
L12

Flat helpers, depth one

CHOICE
Helpers cannot start helpers; at most four at once; always a structured report.
WHY
What nearly every harness converged on: nested agents are hard to bound and debug.
COST
No deep trees of agents for very large jobs.
D33

Memory is plain files

CHOICE
A MEMORY.md index per project plus a global one, edited with the normal file tools.
WHY
You can read, fix, grep and version it. No database to corrupt.
COST
No fuzzy semantic search over memory; recall searches sessions by words instead.
D4

Sessions as append-only JSONL

CHOICE
One message per line, written as it happens.
WHY
Resume is reading, fork is copying, a crash loses at most one line.
COST
Listing many sessions means reading many files.
D23

Plain threads, no async runtime

CHOICE
ureq and scoped threads rather than tokio.
WHY
An agent makes one request at a time; a runtime adds weight and start-up work. The whole engine was about 2 MB.
COST
Some libraries assume async and cannot be used.
D10

Speak Claude Code's formats

CHOICE
Read CLAUDE.md, .claude/skills, .mcp.json and Claude Code's hook contract, with AGENTS.md and .agents/skills as primary.
WHY
Your existing setup works on day one.
COST
Small differences must be documented, such as hook timeouts blocking.
D20

A hard spending cap

CHOICE
Check before every call, record after, fail closed.
WHY
Agents loop. A loop on a big model can spend real money in minutes.
COST
You must raise the cap on purpose when you need more.
D36

Signed public releases

CHOICE
Every file signed with minisign; the signature names the version and machine.
WHY
A self-updating program must prove each update is genuine.
COST
One more step in every release.

DESIGN

What we didn't build

Knowing what a tool leaves out tells you as much as knowing what it has. Some of these are coming; some are left out on purpose.

Coming

FeaturePlanUntil then
WindowsPowerShell and Windows paths; no sandbox at first, so commands askWSL with the Linux build
A to-do listOnly for models that need it; frontier models plan fine on their ownAsk Uno to keep a TODO.md
Asking you questions mid-task1 to 4 questions with options; never in headless runs or helpersIt stops and asks in its answer
uno scheduleWrites a cron, launchd or systemd entry; no background daemoncron plus uno -p
--output stream-jsonEvents as they happen, for other programs--output json at the end

Later, maybe

  • IDE plugins, cloud runs, parallel sessions in worktrees, language servers. Out of scope for version 1. The tool layer is built so remote execution can be added without a rewrite.
  • Helpers you can talk to again. Today a helper reports and is done.
  • A persistent code REPL. Useful for cheap experiments; if added, it will run your own interpreter through the guard.

Not on purpose

  • An agent framework or workflow graph. The model plans; Uno gives it tools.
  • An embedded JavaScript or Python runtime. Weight and attack surface for little gain.
  • A vector database for memory. Plain files you can read beat embeddings you can't.
  • Nested agents. Depth one is easier to bound and debug.
  • Retrying after a tool call was shown. A retry could run a command twice.
  • Trusting a hook's "allow". Hooks can only make things stricter.
